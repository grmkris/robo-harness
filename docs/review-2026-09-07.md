**Findings to address first**

| Priority | Finding and evidence | Proposed change and acceptance |
| --- | --- | --- |
| P1 | **A slow motor read can be followed by motion after lease expiry.** In [engine.py](../python/robo_harness/engine.py), lines 279–293 read the clock before `driver.read()` and use that old value for deadline and expiry checks. Lines 317–332 can then advance and write a command. A fake read advancing time by 3.1 seconds left an expired lease active and wrote a new shoulder target. | Recheck monotonic time after blocking I/O and immediately before advancing motion. Cancel on an overrun and preserve the last commanded hold target. Bound driver read/write timeouts; keep leader read/close and FK costs visible. Test slow follower reads, slow leader reads, lease expiry during I/O, and stop contention. A stalled serial call cannot be made interruptible merely by adding a Python timer. |
| P1 | **Camera latency can make an old observation appear freshly received.** [robot.ts](../apps/server/src/robot.ts), lines 66–86, waits for `/observe` and both JPEG requests together, then assigns their common completion time to `receivedAt`. An observation returned early can spend up to the camera timeout waiting while its reported age stays unchanged. The clock-offset estimate includes that unrelated delay. | Sample observations and cameras independently; timestamp each response on receipt and account conservatively for transit time. Enforce one total-age bound. A delayed camera must not delay joint-status publication or reset an old observation's freshness. Python checks remain a separate protection; this finding concerns the coordinator's view and recordings. |
| P1 before paid activation | **Ambiguous inference submissions can refund reserved spending.** [perception.ts](../apps/server/src/perception.ts), lines 108–130 and 232–238, only marks a job charged after a successful HTTP response. If the provider accepted the job but its response was lost, the catch path refunds the reservation. This contradicts [the documented uncertain-billing policy](perception.md). This is a code-path finding, not a measured billing incident. | Persist `reserved`, `submitted`, `unknown`, `completed`, and confirmed rejection states with provider request IDs. Preserve the reservation when acceptance is uncertain; refund only on evidence of non-acceptance. Test a fixture that accepts a request and drops the response, restart recovery, and concurrent budget requests. |
| P2 | **Event reconnects can skip evidence.** [main.ts](../apps/server/src/main.ts), line 236, emits SSE `data` without SSE `id`, although the handler reads `Last-Event-ID`. [store.ts](../apps/server/src/store.ts), line 36, selects the newest 200 events after the cursor. More than 200 pending events skips the earliest part of the gap; telemetry then advances past it. | Emit SSE IDs; page forward in ascending ID order. Give reconnecting clients a snapshot/cursor contract and report unrecoverable gaps. Verify a disconnect spanning more than 200 events without missing or duplicating action records. |
| P2 | **A recording can report captured despite losing event/program artifacts.** [main.ts](../apps/server/src/main.ts), line 529, discards `recordEvent()` failures. [recordings.ts](../apps/server/src/recordings.ts), lines 188–206, waits for sample writes but not outstanding event writes before deciding completeness. | Give each recording a bounded writer queue, track all artifact failures, and drain it before finalization. Atomically finalize the manifest. Fault-inject event-write errors, missing program artifacts, concurrent stop/start, and shutdown during writes. Preserve the SQLite journal as a recovery source. |
| P2 | **Boundary conformance is unfinished.** [The web client](../apps/web/src/lib/client.ts) trusts `response.json()` through a generic return type; [the CLI client](../packages/protocol/src/client.ts) casts results. Python `Move` uses coercing Pydantic fields: a probe converted `true` to joint angle `1.0` and string `"1"` to duration `1.0`. | Decode browser, CLI, SSE, and Python boundaries consistently. Add shared conformance fixtures covering booleans, strings, NaN, unknown fields, dimensions, and operation states. The coordinator already rejects several bad inputs; the internal Python boundary should independently agree. |

The slow-read probe used only `MockDriver`, the checked-in example profile, the real `Engine`, and an injected clock. At simulated time `103.1333`, a lease expiring at `103.0` remained present, the operation remained `running`, and the driver received shoulder target `0.0666667`. This demonstrates a software failure path, not an observation of the physical arm.

**What the perception feature actually provides**

| Capability | Implemented behavior | Meaning for the robot |
| --- | --- | --- |
| SAM 3 segmentation | Send one workspace/wrist image and a phrase such as “red cup”; receive pixel masks, scores, and an overlay. | Identifies image regions. It does not itself establish distance, a grasp pose, or a safe path. |
| Depth Anything 3 | The GPU worker estimates depth from one image; returns a preview plus a 160×120 numeric map and its image-coordinate mapping. Our worker always labels this output `relative`. | Estimates near/far structure. It is not a LiDAR measurement or a calibrated distance in meters. |
| Rerun visualization | Shows source images, masks/depth previews, frame IDs, and robot geometry. Relative depth is logged as a tensor; a result explicitly marked meters can be logged as a depth image. | Helps inspect results and provenance. Displaying a result does not make it safe for motion. |
| Provider integration | A private GPU `/infer` worker or a fal queue endpoint implementing our custom contract. | Both routes are implemented as integration scaffolding; neither is configured in the live harness. |

For a cup-picking task, segmentation answers “which pixels are the cup?” Depth estimation suggests its shape and relative distance. Moving the gripper there additionally needs camera intrinsics, camera-to-robot transforms, a trusted scale/depth source or a calibrated tabletop assumption, a grasp estimate, and a checked motion plan. The current empty camera calibration and disabled Cartesian commissioning correctly prevent claiming this pipeline is ready.

SAM 3's upstream model supports promptable segmentation. DA3 has several model families, including metric variants, but that does not change the current worker's relative-output contract; switching requires a tested calibration and units path. [SAM 3 source](https://github.com/facebookresearch/sam3), [Depth Anything 3 source and model table](https://github.com/ByteDance-Seed/Depth-Anything-3).

**The fal key and practical activation path**

Confirmed a nonempty `FAL_KEY` in Sonara's Railway project, production environment, server service. Its value was processed only in memory and never printed or written to this repository. The user does not need to paste it into chat. This was a presence/access check, not a fal authentication or billing test. It has not been installed into Robo Harness.

The existing `ROBO_FAL_ENDPOINT` expects our `{ kind, prompt, frame }` input and normalized provenance-rich output. Catalog endpoints have their own schemas, so setting a key and a model name alone will not work.

Recommended first adapter: `fal-ai/sam-3/image`. Convert the captured image to the documented `image_url` input (a data URI is supported), map the text prompt, download and validate returned masks, and retain the original frame ID and geometry locally. The endpoint returns image/mask objects and metadata rather than our current worker envelope. [fal SAM 3 API](https://fal.ai/models/fal-ai/sam-3/image/api).

For depth, the verified hosted image endpoint is `fal-ai/image-preprocessors/depth-anything/v2`. Its documented result is an image; it is a different model and output contract from our DA3 worker. Treat an adapter as a relative-depth preview unless a tested numeric interpretation is available. I did not verify a hosted DA3 image endpoint in this search. To retain DA3 with numeric output, package the existing GPU worker with pinned model packages/checkpoints and use a compatible host. The current `perception` extra does not install `sam3` or `depth_anything_3`. [fal Depth Anything V2 API](https://fal.ai/models/fal-ai/image-preprocessors/depth-anything/v2/api).

Before live inference, complete the adapters and uncertain-billing handling, configure per-capability conservative costs, install the credential only in the deployment's protected environment, and obtain the operator's aggregate spending cap. Current status has no approved cap. Offline fixtures can validate all request/response conversions first.

Improve the perception panel to state which model is available, why a capability is unavailable, what one request reserves, which frame was analyzed, and whether depth is relative or metric. Keep original-frame/result overlays together. The current special image delivery for `perceive` to MCP/model vision channels is recorded separately in [the pending proposal](perception-image-review.md); it is not an implemented capability.

**Robotics improvements beyond the immediate defects**

1. **Monitor trajectory tracking, not just the final target.** Current execution interpolates positions linearly and declares completion on one within-tolerance sample after the duration. Add per-joint tracking-error limits, a stable settling interval, and explicit stalled/contact outcomes. Track actual sent commands if a driver clips targets. LeRobot 0.6.0 returns the applied action for this reason. The ROS joint-trajectory controller's path/goal tolerance and result model is useful design guidance without requiring a ROS migration. [LeRobot follower implementation](https://github.com/huggingface/lerobot/blob/v0.6.0/src/lerobot/robots/so_follower/so_follower.py), [ROS controller contract](https://control.ros.org/jazzy/doc/ros2_controllers/joint_trajectory_controller/doc/userdoc.html).

2. **Make experiments reproducible.** Store source commit, robot profile/calibration hash, model/checkpoint identity, task, outcome, intervention, and termination reason with each recording. Align images, states, and actions using capture timestamps in a declared clock domain. The current exporter resamples `sample_time_ms`, recorded after coordinator file writes, which mixes transport/storage jitter into the training time axis. For higher-rate demonstrations, use a bounded off-loop recorder fed from the motor-owner snapshots, with explicit drop and synchronization policy.

3. **Build fault simulation before a richer simulator.** Extend the existing mock with deterministic lag, dropped samples, blocked reads, jammed joints, camera stalls, and restarts. Run the same ownership/bounds/result contract against every backend. A MuJoCo backend can then add contact and camera scenarios with reviewed geometry and parameters. Menagerie provides useful model-quality guidance, but a model's presence is not calibration evidence. [MuJoCo Menagerie](https://github.com/google-deepmind/mujoco_menagerie).

4. **Commission visual geometry incrementally.** Use the existing OpenCV/SciPy stack for camera calibration and a known tabletop or fiducial task, record reprojection/position error, and verify camera-to-base and wrist-camera transforms before visual picking. Add uncertainty and freshness to proposed grasp targets. Segmentation and learned depth should inform a proposal that still passes the existing motor-owner checks.

5. **Add smoother trajectories only after timing and tracking are measured.** Ruckig is a candidate optional Python dependency for velocity/acceleration/jerk-constrained state-to-state trajectories. Plan outside the motor lock and verify the sampled trajectory against commissioned bounds. Its Community intermediate-waypoint path uses a cloud API; that is unsuitable for this local motor path. Keep independent position and collision checks. [Ruckig implementation and limitations](https://github.com/pantor/ruckig).

6. **Expose a small experiment health view.** Show motor-loop p95/p99 period, read/write duration, tracking residual, camera age, frame/state skew, queue drops, stop acknowledgement latency, and operation outcome. Carry conversation/tool/request/operation/recording IDs through logs and spans. This makes it possible to distinguish model indecision, network latency, stale perception, and a mechanically stalled move.

**Project standards and suggested sequence**

Continue the Effect migration by responsibility, with independent commits and tests. Scope transitional lint exceptions to remaining legacy files and prevent their count from growing. Prioritize unsafe casts and unowned async work over cosmetic rules. Update stale nested `AGENTS.md` statements about Zod and a dependency-free domain package: the code has already moved to Effect Schema. Update validation test counts and the README's obsolete fixed-port description. Add versioned SQLite migrations before evolving the experiment/job tables; `CREATE TABLE IF NOT EXISTS` alone cannot upgrade an existing schema.

Suggested order:

1. Fix the motor-read deadline and coordinator freshness defects; add deterministic failure tests.
2. Finish boundary decoding and loss-aware event/recording delivery, then scoped service ownership.
3. Implement the SAM 3 fal adapter, resolve uncertain billing, and make capability status clear. Activate only within a configured budget; add depth as an explicitly identified backend.
4. Add experiment metadata and capture-time alignment, then fault simulation and a small repeatable manipulation benchmark.
5. Use benchmark evidence to choose smoother trajectories, calibrated visual targeting, and eventually bounded LeRobot policy execution.

This keeps the current standalone architecture and grows it around measured robotics needs. No additional orchestration framework or cross-project runtime dependency is needed for these first improvements.
